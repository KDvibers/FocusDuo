# FocusDuo Desktop

Kotlin/JVM + Compose Desktop для Windows. Самостоятельная сборка: backend не нужен для сборки или запуска этого каталога.

## Обычная установка Windows

Получить MSI с SHA-256 из [протокола](docs/WINDOWS_PACKAGING.md), установить и открыть ярлык FocusDuo. Java/Gradle/WiX на пользовательском ПК не нужны. В форме входа указать базовый адрес общего сервера (например `https://focusduo.example`, без `/api/v1` и `/ws`). Адрес редактируется в UI; пароль и токен не сохраняются, после перезапуска нужен вход. Несекретные настройки `%USERPROFILE%\.focusduo\preferences.properties` сохраняются при обычном удалении. Установщик не содержит backend или PostgreSQL.

### Упаковка разработчиком

Из `desktop/`, Windows x64 / PowerShell 7 / JDK 21 x64:

```powershell
.\package-windows.ps1 -Task version
.\package-windows.ps1 -Task check
.\package-windows.ps1 -Task createDistributable
.\package-windows.ps1 -Task runDistributable
# Закрыть окно образа.
.\package-windows.ps1 -Task packageMsi
```

Скрипт ищет JDK в `FOCUSDUO_JAVA_HOME`, `JAVA_HOME`, пользовательской `.jdks`, затем `PATH`; проверяет JDK 21/Windows/x64 и запускает упаковку тем же JDK. `WIX_PATH` позволяет использовать существующий WiX; иначе плагин загружает WiX 3.11.2. [Полные команды, лицензии, артефакт и матрица приёмки](docs/WINDOWS_PACKAGING.md).

## Запуск разработчиком в PowerShell

Из корня репозитория:

```powershell
# Первый запуск скачивает зависимости. Скрипт ищет JDK 21 в FOCUSDUO_JAVA_HOME,
# JAVA_HOME, затем в пользовательской .jdks и по java из PATH.
powershell -ExecutionPolicy Bypass -File .\desktop\run.ps1 -Demo
```

`ExecutionPolicy Bypass` относится только к этому процессу PowerShell; скрипт не меняет системную политику или постоянные переменные среды. Без `-Demo` открывается вход на настоящий сервер. До отправки формы можно изменить адрес и запоминаемый username; после входа они доступны в настройках:

```powershell
powershell -ExecutionPolicy Bypass -File .\desktop\run.ps1
```

Если автоматический поиск JDK не сработал:

```powershell
$env:FOCUSDUO_JAVA_HOME='C:\путь\к\jdk-21'
powershell -ExecutionPolicy Bypass -File .\desktop\run.ps1 -Demo
```

Прямой запуск и тесты через wrapper:

```powershell
$env:JAVA_HOME='C:\путь\к\jdk-21'
Set-Location desktop
.\gradlew.bat test
.\gradlew.bat run --args="--demo"
.\gradlew.bat run --args="--demo --width=1000 --height=700"
```

Для проверки размера окна также доступно `run.ps1 -Demo -Width 1000 -Height 700`. Свернуть, развернуть, переместить и закрыть окно можно стандартными средствами Windows.

## Что проверить в демо

Следующие действия — инструкция для самостоятельной проверки. Фактические результаты запуска и скриншоты этапа 7 перечислены в [HANDOFF](docs/HANDOFF.md).

Сначала войти в локальный демонстрационный аккаунт `demo_user` / `FocusDuoDemo1!`, явно открыть готовый демовход либо зарегистрировать свой демоаккаунт. Пароль тестового аккаунта является публичным примером и не предназначен для реальных учётных записей. Регистрация проверяет username (3–32 символа `a-z`, цифры, underscore), имя (2–40 после trim) и пароль (10–128 без trim). Сервер при этом не вызывается.

1. На главной нажать «Создать комнату»: по умолчанию 25 минут фокуса и 5 минут перерыва. Новая комната содержит одного участника, пустые цель и задачи.
2. Изменить свою цель, добавить задачу, отредактировать её, отметить выполнение и удалить. Цель — до 240 символов; название задачи — 1–160 после удаления пробелов по краям; максимум 20 задач у каждого участника.
3. Скопировать код кнопкой в заголовке или открыть «Пригласить». Код попадает в системный буфер обмена; внешние приглашения не отправляются.
4. В блоке «Управление демо» нажать «Добавить демоучастника», затем «Сменить участника». Собственная карточка меняется вслед за выбранным пользователем; чужие задачи доступны только для чтения. Роль создателя остаётся привязанной к владельцу комнаты.
5. От имени создателя изменить длительности: фокус 5–180 целых минут, перерыв 1–60. Настройки доступны только вне активного раунда; другой участник не может их менять.
6. Для готового примера использовать «Открыть пример комнаты» на главной или «Войти по коду» с `FD-DEMO42`. Регистр и пробелы по краям кода не важны. Неизвестный код показывает ошибку.
7. От имени создателя нажать «Начать фокус». Для запуска нужны два участника. У подготовленного примера создатель — другой участник: сначала нажать «Сменить участника» в инструментах демо.
8. Проверить отсчёт, «Пауза» и «Продолжить». На паузе остаток заморожен, её время не входит в итог. Только создатель управляет раундом; у другого участника соответствующие действия недоступны.
9. Завершить раунд вручную и проверить итог с фактическим активным временем, целями, задачами и счётчиками обоих. Вернуться в комнату, изменить задачу и открыть итог снова: сохранённая копия не меняется.
10. После завершённого FOCUS отдельно запустить «Начать перерыв». Следующий фокус тоже запускается вручную. Перерыв является отдельным раундом; повторный BREAK сразу после BREAK недоступен.
11. Для быстрой проверки автозавершения использовать явные инструменты демо «+1 минута» и «До окончания раунда» во время RUNNING. Они двигают только локальные демочасы, сохраняя допустимые длительности контракта. Итог по времени создаёт `FakeRepository`, а не круговой индикатор.
12. Нажать «Закрыть комнату» и подтвердить. Это доступно обоим участникам: активный раунд отменяется с отдельным итогом, завершённый результат сохраняется. Закрытая комната доступна для просмотра; на главной можно создать новую.
13. «Сбросить демо» с подтверждением удаляет локальную комнату, задачи и историю и возвращает на главную. Это инструмент демонстрации, отдельный от закрытия комнаты. Имя основного демопользователя сохраняется до закрытия приложения.
14. В разделе «История» открыть завершённый или прерванный раунд; проверить фильтры «Все», «Фокус», «Перерыв» и возврат из подробного итога. В списке максимум 50 результатов, даты окончания показываются в локальном часовом поясе. Суммы за всё время не вычисляются.
15. Явными инструментами демо проверить загрузку и ошибку истории; кнопка повтора возвращает обычное состояние. При отсутствии результатов доступен переход на главную; пустой фильтр предлагает показать все.
16. В настройках изменить адрес сервера и username. Некорректный адрес не сохраняется. Настройка адреса не подключает к сети и не отправляет демоданные. Выйти из аккаунта и войти снова в том же процессе: комната и результаты этого аккаунта сохраняются, активный раунд не закрывается.

Имя редактируется в боковой панели, цель — в своей карточке комнаты. Разделы доступны через навигацию; переход на главную и выход из аккаунта не закрывают комнату. Блок «Управление демо» находится под комнатой и при необходимости доступен прокруткой. Второй пользователь моделируется в одном процессе — это ещё не совместная работа двух приложений. Состояния подключения к серверу и online-присутствия не имитируются.

## Адрес сервера и локальные настройки

По умолчанию используется `http://127.0.0.1:8090`. Нужен адрес сервера без `/api/v1`, другого пути, query, fragment или credentials. Переменная `FOCUSDUO_BASE_URL` задаёт адрес на запуск; иначе используется сохранённая настройка, затем default. Для обычного режима с работающим backend:

```powershell
$env:FOCUSDUO_BASE_URL='http://127.0.0.1:8090'
powershell -ExecutionPolicy Bypass -File .\desktop\run.ps1
```

`127.0.0.1` на каждом ПК указывает на этот же ПК; для двух компьютеров нужен адрес одного общего сервера. HTTP разрешён для локальной разработки, удалённый адрес поддерживает HTTPS/WSS. Ktor не следует перенаправлениям и не пишет запросы, ответы или секреты в лог. При сохранении другого адреса старые запросы отменяются, локальная сессия очищается и требуется новый вход. Это не закрывает комнату и не отправляет logout на прежний сервер. В демо аккаунты разных адресов изолированы в памяти. Пароли и bearer-токены не записываются в preferences.

Файл несекретных настроек по умолчанию: `%USERPROFILE%\.focusduo\preferences.properties` (`baseUrl`, `rememberedUsername`). Некорректные сохранённые значения или переменная окружения дают понятное предупреждение; деморежим автоматически не включается.

## Авторизация и проверка HTTP

Для настоящего входа используйте учётную запись выбранного backend или форму регистрации. Публичный `demo_user` относится только к деморежиму и не создаётся на сервере автоматически. После успешной авторизации клиент отдельно загружает `/me` и текущую комнату; сетевой сбой восстановления оставляет возможность повторить GET без повторного POST входа/регистрации. Ответ `401` очищает локальную сессию и возвращает к входу. Logout вызывает сервер, очищает токен даже при сетевой ошибке и не закрывает комнату. При неподтверждённом logout приложение сообщает, что серверная сессия может оставаться действительной до истечения срока.

Обычный `gradlew.bat test` не требует backend: он проверяет DTO, все 10 исходных JSON-fixtures, mock HTTP, reducer снимков, монотонный отсчёт и TCP-сценарии production CIO с локальными тестовыми HTTP/WS-серверами. Последние проверяют реальный движок и сетевой транспорт, но не являются проверкой Java backend.

После запуска Java backend отдельно выполните из `desktop/`:

```powershell
.\gradlew.bat backendAuthSmoke "-Dfocusduo.smoke.baseUrl=http://127.0.0.1:8090" --console=plain
```

Это явная интеграционная команда без Compose-окна: register → `/me` → `/rooms/current` → logout → login → восстановление → logout через CIO. Она создаёт на выбранном **сервере разработки** новую учётную запись `desktop_<random>`; пароль генерируется в памяти и не выводится. Контракт V1 не содержит удаления аккаунта, поэтому запись остаётся в БД. Backend-разработчик выполнил её на baseline `0fb2b56` с отдельной тестовой Java/PostgreSQL: PASS, [условия и результаты](../docs/backend/RECOVERY_INTEGRATION.md).

Для двух независимых Kotlin-репозиториев и WebSocket добавлена отдельная проверка:

```powershell
.\gradlew.bat backendRoomSmoke "-Dfocusduo.smoke.baseUrl=http://127.0.0.1:8090" --console=plain
```

Она создаёт два аккаунта разработки, создаёт/объединяет комнату, ожидает WS обоих, изменяет цель и задачу, проходит FOCUS → pause/resume → finish → неизменяемый итог, затем BREAK → close. Аккаунты остаются в БД; пароль и токен не печатаются. Эта задача исключена из обычного `test`; прежний backend PASS на baseline `0fb2b56` дополнен новым desktop-повтором в [8.2](docs/STAGE8_2_RECOVERY.md). Дополнительные recovery/restart harness описаны в [RECOVERY_INTEGRATION.md](../docs/backend/RECOVERY_INTEGRATION.md); их новый desktop init и результаты также находятся в протоколе 8.2. Нормальный сценарий двумя Compose-окнами с Java проверен отдельно в [этапе 8.1](docs/STAGE8_1_INTEGRATION.md), GUI-рестарты — в 8.2, физический Modern Standby на `8fdb392` — в [backend-отчёте](../docs/backend/COMPOSE_ACCEPTANCE.md). Последующая удалённая Tailscale-приёмка описана в [backend-отчёте](../docs/backend/REMOTE_ACCEPTANCE_2026-10-12.md); она не заменяет установленный MSI или обычный LAN без VPN.

Для повторения именно GUI-сценария предусмотрены изолированный native Windows runtime и два профиля запуска; prerequisites и проверенные PowerShell-команды — в [протоколе 8.1](docs/STAGE8_1_INTEGRATION.md#воспроизведение). Сервер использует временный PostgreSQL на отдельном порту, обычные пользовательские настройки клиента и существующая БД не затрагиваются.

Для воспроизводимой визуальной проверки сетевых состояний подготовлен отдельный **тестовый стенд** в `src/test/kotlin/dev/focusduo/qa/ContractUiServer.kt`. Он слушает только loopback `127.0.0.1:18090`, хранит синтетические данные в памяти и запускается явно из `desktop/`:

```powershell
.\gradlew.bat contractUiServer --console=plain
```

Во втором терминале из корня репозитория:

```powershell
$env:FOCUSDUO_BASE_URL='http://127.0.0.1:18090'
powershell -NoProfile -ExecutionPolicy Bypass -File .\desktop\run.ps1
```

Вход: `qa_desktop` / `FocusDuoQa123!` (публичные синтетические credentials стенда). Управление стендом: `Invoke-RestMethod -Method Post http://127.0.0.1:18090/_qa/mode/lost` задаёт 500 после сохранения следующей задачи, `conflict` — конфликт следующей задачи, `offline`/`online` — недоступность/восстановление, `disconnect` — разрыв WS, `expired` — WS 4401, `close` — закрытие комнаты. `Invoke-RestMethod http://127.0.0.1:18090/_qa/state` показывает счётчики записей и replay. Стенд поддерживает только эти визуальные сценарии и добавление задач; он не заменяет полный backend, Java-интеграцию или деморежим приложения.

## Комната, WebSocket и серверный таймер

Создать комнату или войти по коду можно на главной. Код является непрозрачной строкой сервера; клиент нормализует только trim/uppercase. Каждый редактирует собственные цель и задачи, владелец управляет длительностями и раундами, любой участник может явно закрыть комнату для обоих. Приглашение копирует код локально. Все изменения отправляются по REST с новым UUID `Idempotency-Key`; для существующей комнаты также передаётся текущая `X-Room-Revision`. WebSocket передаёт полные `ROOM_SNAPSHOT`, bearer находится только в заголовке handshake; используется [Ktor Client WebSockets](https://ktor.io/docs/client-websockets.html) без STOMP/SockJS.

В пределах одной комнаты меньшая revision игнорируется. Равная revision с более новым `serverNow` уточняет вычисленные временные поля, сохраняя задачи и другие бизнес-данные. Новый roomId начинает независимый порядок; сообщения прежнего подключения отбрасываются. При `REVISION_CONFLICT` актуальный snapshot применяется, ошибка показывается пользователю, автоматического повторения команды нет.

Отображение RUNNING привязано к `serverNow`/`endsAt` и `System.nanoTime`, PAUSED сохраняет замороженный остаток. При нуле интерфейс ждёт подтверждения сервера: он не меняет статус и не создаёт результат. COMPLETED/CANCELLED показывает фактическое активное время из backend, включая досрочное завершение. История и детали загружаются отдельными GET и содержат серверные копии задач. «В фокусе» относится к раунду и не означает отдельное online-присутствие друга.

При разрыве WS восстановление выполняется автоматически: базовые задержки 1, 2, 4, 8, 16 и 30 секунд, jitter 0.8–1.2 с абсолютным пределом 30 секунд. Во время сетевой недоступности число попыток не ограничено; logout/смена сервера отменяет цикл. Сначала клиент читает текущую комнату по REST, затем ждёт свежий полный WS-снимок; до завершения синхронизации изменения отключены. Старые поколения соединений и устаревший первый снимок не разрешают команды. `401`/`4401` и ожидаемое закрытие CLOSED-комнаты останавливают восстановление. `403`/`404` и некорректный протокол приостанавливают автоматические попытки и оставляют ручное обновление.

Heartbeat проверяет разрыв выполнения от 10 секунд по календарным и монотонным часам, поэтому учитывает платформы, где `nanoTime` включает сон или останавливается на его время. Возврат фокуса/разворачивание после отсутствия от 5 секунд тоже запрашивает синхронизацию. Короткие переключения фокуса и обратная коррекция календарных часов сами по себе не запускают её. Это обнаружение необходимости обновить состояние, а не точный системный датчик сна. Реальный Modern Standby проверен на `8fdb392` с активацией окон при осмотре; другие режимы сна, точная задержка и восстановление без foreground не заявляются.

Ошибка отправки не означает, что сервер точно не выполнил команду. При неоднозначном исходе сохраняются исходные method/path/body, Idempotency-Key и revision, блокируются новые команды и восстанавливается состояние. Пользователь может явно повторить этот же запрос; автоматического повторного POST/PATCH/DELETE нет. Закрытие формы сохраняет pending; выход из сессии удаляет его вместе с токеном, поэтому после нового входа нужно проверить результат на сервере. Подробное поведение и ограничения — в [HANDOFF](docs/HANDOFF.md).
