# Разбор замечания о восстановлении после сна

Дата: 11 октября 2026. Исправление клиента подготовлено отдельной веткой `feat/desktop-wake-recovery` от `main` `8310e23`, после интеграционного PR #13. Изменения ограничены `desktop/**`; production Java, PostgreSQL, общий контракт и fixtures не менялись.

## Вывод для backend-разработчика

Замечание подтверждено: ошибка находилась в ограничении частоты восстановления в Compose workspace, а не в `ResumeDetector`, `RealRepository` или сервере. Детектор учитывал календарные и монотонные часы, но следующий UI-барьер проверял только `nanoTime`. Если эти часы почти не продвинулись во сне, барьер мог поглотить уже обнаруженный сигнал и оставить прежнюю привязку таймера до другого триггера восстановления.

Точный сценарий с управляемыми часами:

1. Последнее восстановление и исходный heartbeat: wall = `1_000_000 ms`, nano = `100_000_000_000 ns`.
2. Проходит 60 секунд сна при остановленных монотонных часах и 1 секунда активности: wall = `1_061_000 ms`, nano = `101_000_000_000 ns`.
3. `ResumeDetector` видит календарный разрыв 61 секунду, возвращает `true` и обновляет baseline.
4. Прежний барьер видит только 1 секунду по nano, отбрасывает событие как слишком частое. Следующий heartbeat видит обычный секундный интервал и не повторяет потерянный сигнал.

Это условный дефект кода; физический сон Windows таким сценарием не воспроизводился. Ошибка не означает, что каждое пробуждение обязательно ломало восстановление: другой сигнал окна или отказ WS мог запустить новый цикл.

## Почему 171 тест и живая интеграция проходили

Прежние 12 clock-тестов проверяли `ResumeDetector` отдельно, в том числе остановленные монотонные часы. Они не проходили следующий барьер Compose. Recovery/restart harness из backend PR #13 проверяют настоящий Kotlin repository, CIO, Java и PostgreSQL; явный `recoverAfterResume()` вызывается непосредственно у repository. Поэтому путь «детектор → ограничение частоты UI → восстановление» ими не проверялся. Успешные результаты repository и найденное замечание по Compose совместимы.

Подтверждённые backend-разработчиком результаты сохранены в [RECOVERY_INTEGRATION.md](../../docs/backend/RECOVERY_INTEGRATION.md): 171 обычный тест + 2 живых smoke, recovery harness с 4 checkpoints и restart harness с 5 checkpoints. Проверены точный replay без второго эффекта, настоящий 409 и автоматическое восстановление двух repository после двух перезапусков Java с той же PostgreSQL. В этом исправлении эти живые сценарии повторно не запускались.

## Исправление клиента

`ResumeRecoveryCoordinator` объединяет production-путь heartbeat и уже квалифицированные foreground-сигналы. `RealWorkspace` вызывает тот же координатор, который проверяется управляемыми часами. Минимальный интервал 2 секунды выполнен, если достаточный разрыв есть хотя бы по одному источнику времени: nano или календарным часам. Обратная коррекция календаря сама по себе восстановление не разрешает. Mutex не допускает одновременных вызовов; обычные дубли heartbeat/focus в пределах интервала остаются подавлены.

Так барьер сохраняет защиту от частых вызовов и пропускает календарный разрыв при остановленных монотонных часах. Формы, pending/replay, revision и правила серверного таймера не изменены.

## Проверка исправления

Новые тесты сначала запущены на сохранённом прежнем nano-only алгоритме. Получено ожидаемое падение 5 из 13 coordinator-тестов (точный wake-сценарий, оба порядка сигналов, календарная граница и переполнение) и единственного seam-теста с настоящим `RealRepository`: wake должен немедленно запретить изменения до окончания авторитетных чтений. Это подтверждает, что тесты обнаруживают прежний дефект.

После исправления Windows / JDK 21: `gradlew.bat check --console=plain` — **BUILD SUCCESSFUL за 8 секунд, exit 0**. Независимый подсчёт XML: **185 тестов, 0 failures, 0 errors, 0 skipped** = прежние 171 + 13 `ResumeRecoveryCoordinatorTest` + 1 repository seam-тест. Управляемые часы проходят тот же production-координатор, который использует Compose workspace, и доходят до реального `recoverAfterResume()` с проверкой немедленной блокировки команд; транспорт управляемый, Java/PostgreSQL не участвуют. После финального прогона production-код не менялся.

Снимки относятся к предыдущему GUI-сеансу; после данного clock-исправления новый GUI-сеанс не заявляется. Проверка через тестовый стенд не выдаётся за GUI-проверку с Java backend.
