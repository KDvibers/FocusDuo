## Добавлено на этапе 7

- После неожиданного разрыва транспорт автоматически восстанавливается с экспоненциальным backoff: базовые задержки 1, 2, 4, 8, 16, 30 секунд и jitter 0.8–1.2, итоговая задержка не более 30 секунд. Число попыток при сетевой недоступности не ограничено; жизненный цикл сессии отменяет worker. Новый цикл читает текущую комнату через REST и ожидает актуальный полный WS-снимок. До этого изменяющие действия заблокированы; поздние сообщения прежних поколений и старый первый snapshot не разблокируют клиент. `403`/`404` и ошибочный протокол приостанавливают автоматические попытки и оставляют ручную кнопку восстановления.
- Создание и вход в комнату тоже ждут восстановления членства через GET, даже если до перерыва известной комнаты не было. Это исключает отправку новой команды на основе устаревшего предположения «комнаты нет».
- Пробуждение определяется как необходимость синхронизации: heartbeat раз в секунду сравнивает оба источника времени и обнаруживает разрыв от 10 секунд. Это учитывает платформы с продолжающимся или остановленным `nanoTime` во время сна. Возвращение фокуса/восстановление окна после отсутствия от 5 секунд даёт дополнительный сигнал; initial focus, короткие диалоги и повтор focus + restore не создают лишний цикл. Обратная коррекция календарных часов сама по себе не считается пробуждением. Коррекция часов вперёд может вызвать безопасное обновление.
- `Main` устанавливает и снимает AWT-слушатели вместе с окном. Жизненный цикл реального workspace отменяет heartbeat/collectors при logout, смене сервера и закрытии. Сигналы восстановления объединяются с debounce 2 секунды; черновики форм остаются в UI. После обнаружения паузы изменения блокируются сразу, даже если прежний HTTP ещё ожидает ответа; безопасное чтение ждёт освобождения общего mutex запросов. Клиент вновь запрашивает серверное состояние, не создавая локальный результат таймера.
- При неоднозначном результате отправки (сеть, timeout, некорректный ответ, 5xx или неизвестный HTTP-исход) исходные method/path/body/Idempotency-Key/X-Room-Revision сохраняются в памяти. Интерфейс показывает неразрешённое действие, предлагает обновить состояние и повторить тот же запрос. Новые команды блокируются; replay не меняет payload, ключ или исходную revision. Закрытие формы не удаляет pending; выход из сессии очищает pending и токен, поэтому после нового входа нужно проверить серверный результат. После `REVISION_CONFLICT` применяется актуальный snapshot, автоматического нового действия нет; сохранённый черновик можно проверить и отправить осознанно. Безопасные GET при временной сетевой/timeout/5xx-ошибке повторяются в цикле восстановления; POST/PATCH/DELETE автоматически не повторяются.
- Поля формы с неразрешённым запросом временно доступны только для чтения: повтор относится к первоначально отправленным значениям и не может незаметно удалить новый ввод. При обычном разрыве связи без pending поля продолжают редактироваться, а отправка ждёт синхронизации. После конфликта форма показывает серверные значения и требует явного подтверждения проверки перед новым действием.
- Закрытая комната, `401`/WS `4401`, logout, смена сервера и закрытие клиента прекращают восстановление. Обычный обрыв сети не включает деморежим и не отправляет close-room. Кнопка ручного обновления остаётся доступной.
- Добавлены детерминированные тесты heartbeat/focus с движущимися и остановленными часами, обратной коррекцией календаря, signed nanoTime wrap и дедупликацией восстановления окна. Транспортные тесты проверяют reconnect, запросы с исходным ключом и revision, конфликты и жизненный цикл.

## Добавлено на этапе 6

- `RealRepository` выполняет create/join, редактирование своей цели, CRUD своих задач, настройки владельца, запуск FOCUS/BREAK, pause/resume/finish по конкретному roundId и явное закрытие комнаты. Методы/пути/JSON соответствуют V1; команды изменения получают UUID `Idempotency-Key`, команды существующей комнаты — `X-Room-Revision`. Автоматических повторов команд нет.
- История `/history` и отдельный `/history/{roundId}` приходят с backend. Главная, комната, формы, история, детали и настройки реального режима подключены к серверному репозиторию. Черновики форм сохраняются при входящих снимках; чужие задачи и действия владельца защищены интерфейсом и сервером. Демоинструменты в настоящем режиме отсутствуют.
- Ktor raw JSON WebSocket `/ws/rooms/{roomId}` с bearer в заголовке handshake и стандартными control frames. Локальный статус отражает подключение/ожидание полного снимка/готовность/разрыв; до нового полного snapshot изменяющие действия блокируются. Повтор подключения на этом этапе ручной. Сокет отменяется при смене комнаты, logout, истечении сессии и закрытии клиента; поздние сообщения предыдущего подключения игнорируются.
- Общий `RoomSnapshotReducer` для REST/WS/idempotent replay сравнивает revision только при совпадении roomId. Меньшая revision игнорируется; большая заменяет бизнес-данные; равная с новым serverNow уточняет только вычисленные временные поля. Задачи, цели, состояние и идентификатор раунда не откатываются. `REVISION_CONFLICT` применяет snapshot и возвращает понятную ошибку без безусловного повтора.
- Неоднозначный исход отправки останавливает stream и блокирует новые изменения до нового актуального полного снимка. Для create/join дополнительно требуется GET текущей комнаты, чтобы восстановить неизвестный результат членства. Старый первый WS-снимок после reconnect не разрешает изменения. Исходный запрос не повторяется автоматически; сохранение method/path/body/ключа/revision для повтора остаётся этапом 7.
- `ServerTimer` привязывает `serverNow`/`endsAt` к локальному `System.nanoTime`. Отображение RUNNING обновляется отдельно от серверного StateFlow; PAUSED не движется. Ноль сохраняет RUNNING и ожидание подтверждения backend, не создавая историю. COMPLETED/CANCELLED сохраняет фактическое активное время, а не плановую длительность. Повтор старого снимка не перезапускает локальный отсчёт; предусмотрена необязательная поправка на измеренную задержку транспорта.
- Ошибки полей комнаты используют разрешённые поля; произвольные ответы сервера, stack trace и секреты не попадают в UI. HTTP `401` и WS `4401` очищают сессию. Подключение HTTPS преобразуется в WSS без credentials/query в URL. Потеря связи, logout, выход из приложения и смена URL не закрывают комнату.
- Добавлены unit/contract-проверки команд и заголовков, HTTP/WS ordering/lifecycle, монотонного отсчёта, reducer и транспортные проверки production CIO с локальными тестовыми серверами. Задача `backendRoomSmoke` выполняет сценарий двух настоящих Kotlin-репозиториев с Java backend без Compose-окна; она исключена из обычного `test`.

Поддержаны default `http://127.0.0.1:8090`, приоритет `FOCUSDUO_BASE_URL`, проверка адреса и явный logout. - Незавершённый ввод настроек и форм не перезаписывается при обновлении комнаты. Автоматический итог открывается только на главной/в комнате без активного диалога; на остальных экранах показывается уведомление и новый результат становится доступен в истории. Ограничения длины auth/profile/goal/task согласованы по Unicode code points.

## База из этапов 1–3

- Самостоятельная desktop-сборка: Kotlin/JVM 2.2.20, Compose Desktop 1.9.1, Gradle Wrapper 8.13 с SHA-256 и Java toolchain 21. PowerShell-скрипт находит JDK 21 без изменения постоянных системных настроек.
- Светло-зелёные компоненты Compose, Manrope с кириллицей, согласованные Canvas-иконки, системная рамка Windows. Комната сохраняет круговой таймер слева, участников под ним и карточки задач справа; узкое окно использует одну колонку и прокрутку.
- Явное включение демо через `--demo` или стартовый экран. В заголовке окна и интерфейсе видна пометка режима; серверные соединения не создаются.
- `FocusDuoRepository`, локальный `FakeRepository` и `StateFlow`. Изменения сериализуются через `Mutex`; снимки и история содержат неизменяемые списки.
- Создание пустой комнаты, вход в подготовленный пример `FD-DEMO42`, приглашение и копирование кода через clipboard. Локальный пример открывается от имени обычного участника; для управления таймером можно переключиться на создателя.
- Собственная цель до 240 символов; добавление, редактирование, отметка и удаление собственных задач. Название после trim содержит 1–160 символов; максимум 20 задач у каждого участника. Чужие задачи доступны только для чтения, в том числе владельцу комнаты.
- Настройки длительности: фокус 5–180, перерыв 1–60 целых минут. Их меняет только создатель вне RUNNING/PAUSED.
- FOCUS запускается владельцем при двух участниках и отсутствии активного раунда. BREAK запускается отдельно после текущего COMPLETED FOCUS. Следующий рабочий раунд тоже запускается вручную.
- Отсчёт и круговой прогресс связаны со снимком репозитория. В демо монотонные часы защищают отсчёт от коррекции системного времени; UI регулярно запрашивает свежий снимок. Обычные тики обновляют временные поля без изменения revision.
- Пауза замораживает остаток и активное время, продолжение сохраняет исходный startedAt и устанавливает новый срок из остатка. Только владелец управляет раундом. Команды адресуют конкретный текущий roundId.
- Ручное завершение фиксирует COMPLETED/MANUAL и фактическое активное время без пауз. Автозавершение фиксирует COMPLETED/ELAPSED с endedAt, равным сроку окончания даже при поздней обработке. Завершение и историю создаёт `FakeRepository`, а не круговой индикатор.
- Итог показывает тип раунда, реальное активное время, плановую длительность, цели, задачи и счётчики обоих. У досрочного завершения, окончания по времени и отмены разные подписи. История фиксирует копию один раз по roundId; дальнейшие изменения задач, целей и имён не меняют старый результат.
- Явное закрытие комнаты с подтверждением доступно обоим. Активный раунд становится CANCELLED/ROOM_CLOSED; уже завершённый результат сохраняется. Закрытая комната доступна для просмотра, её изменения запрещены; на главной можно создать новую комнату. Закрытие окна является отдельным действием приложения.
- В состоянии хранятся последние 50 результатов по endedAt и roundId. На этапе 3 был доступен отдельный итог; этап 4 добавляет общий список и детали. Это не статистика за всё время.
- Инструменты демо: присоединение партнёра, смена точки зрения, локальное имя, сброс с подтверждением, продвижение демочасов «+1 минута» и «До окончания раунда» во время RUNNING. Они не расширяют API и не отправляются серверу.

## Точные ограничения

1. Демоаккаунты, хеши демопаролей, комнаты и результаты хранятся только в памяти одного процесса. Перезапуск удаляет их; сброс удаляет комнату и результаты текущего демоаккаунта. Второй демоучастник моделируется локально. Нормальный сценарий двух настоящих Compose-окон с Java проверен на одном ПК в 8.1; PAUSED/RUNNING recovery проверено в 8.2 по USER_REPORTED, снимкам и SQL. LAN ещё не проверен. Дефект автоперехода участника на следующий BREAK-итог исправлен и проверен в двух свежих JVM.
2. Реальная авторизация проверена mock/TCP-сценариями, живым auth smoke в PR #13 и регистрацией/повторным входом через Java в 8.1. Preferences сохраняют лишь URL и username; токен/пароль не сохраняются. Изменение имени в демо не является серверным редактированием профиля. На перезапуске нужен новый вход, refresh-token в V1 нет. TTL PT30S через настоящий UI и Java проверен отдельно в 8.2 на baseline 0da9c6c с неизменённым auth-кодом: автоматический возврат ко входу с пустым паролем, без reconnect-loop.
3. Автоматическое восстановление выполняет только безопасные чтения и WS-подключение. Неоднозначная команда повторяется явно с исходным запросом/ключом/revision; pending хранится только в RAM и теряется при выходе или перезапуске. Перед новым действием после такого выхода нужно проверить серверное состояние. Достижение нуля в UI не создаёт серверную историю. Физический Modern Standby PAUSED/RUNNING подтверждён на `8fdb392`, на последней сборке не повторялся; задержка и восстановление без активации окон не измерены. Переподключение реального сетевого пути/адаптера не проверено; heartbeat/focus являются сигналами обновления, а не гарантированным системным событием сна.
4. Все 10 JSON-fixtures проверены: в прогоне 8.2 совпадают Git blobs, LF-normalized bytes и JSON; raw checkout SHA различается из-за CRLF/LF. Java recovery/restart harness повторены в 8.2 на baseline 0da9c6c, 19 checkpoints / 4 PASS. PAUSED/RUNNING двух окон проверены; после navigation-fix final 199 + 2 и оба свежих JVM подтвердили offline 00:00 и автоматические BREAK-итоги. Отдельный просроченный FOCUS подтверждён 12 октября на `1a6fa94`: оба автоматических итога и единственная ELAPSED-история 300000 ms с исходным deadline. LAN/обрыв сети не проверены. История V1 ограничена последними 50 раундами без пагинации.
5. Фактический промежуточный Compose-аудит этапа 7 описан выше. Loading авторизации наблюдался визуально, но отдельный loading истории в этом GUI-сеансе не проверялся. Полный аудит доступности, пиксельная проверка всех состояний и заключительная визуальная регрессия остаются в этапе 9. После просмотра результата выполнить в PowerShell по очереди. Если команда завершилась ошибкой, следующую не выполнять:

```powershell
Set-Location "C:\Users\user\.codex\worktrees\desktop-wake-recovery\focusDuo"
git status --short --branch
git add -- desktop
git diff --cached --stat
git commit -m "test(desktop): verify expired focus recovery in Compose"
git push -u origin feat/desktop-focus-expiry
```

Перед коммитом убедиться по списку staged-файлов, что включены только нужные desktop-изменения. Push отправляет отдельную ветку `feat/desktop-focus-expiry`; base PR — `main` (`1a6fa94`, уже содержит PR #17/#18). [Текущий PR](PR_FOCUS_EXPIRY.md) относится к отдельной проверке просроченного FOCUS. Прежние описания [8.2](PR_STAGE_8_2.md), [8.1](PR_STAGE_8_1.md), [wake-исправления](PR_WAKE_RECOVERY.md) и [этапа 7](PR_STAGE_7.md) сохранены отдельно. Commit/push/PR в этом заходе автоматически не выполнялись.
