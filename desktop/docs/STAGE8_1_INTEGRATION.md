## Обнаруженный дефект logout

При явном выходе второго пользователя backend отзывает сессию и закрывает WebSocket кодом `4401`. Клиент мог обработать это закрытие раньше успешного HTTP logout и показать на экране входа красное сообщение «сессия истекла» после добровольного выхода. Сессия фактически завершалась; данные комнаты и история не терялись. [Снимок обнаруженного дефекта](screenshots/stage-8-1-guest-logged-out.png).

В `RealSessionController` добавлен явный маркер repository, для которого выполняется добровольный logout. Ожидаемый `EXPIRED` этого repository во время выхода не публикует ошибку и не закрывает HTTP-клиент до ответа logout. Настоящее истечение сессии вне добровольного выхода сохраняет прежнее поведение.

Добавлены два регрессионных теста с настоящим CIO/WebSocket: сервер закрывает WS до удержанного HTTP `204` при logout, а также отдельный случай настоящего expiry. На старом алгоритме первый тест падал, настоящий expiry проходил; после исправления **14 targeted-тестов (2 новых + 12 controller) прошли за 3 секунды**. Полный `gradlew.bat check --console=plain`: **BUILD SUCCESSFUL за 9 секунд, 187 тестов, 0 failures/errors/skipped**, [машиночитаемый результат](evidence/stage-8-1-check.json). Штатный `401`/`4401` не скрывается вне добровольного выхода.

**GUI-повтор исправления — PASS:** запущен новый JVM-процесс с неизменяемым application JAR, HWND `526870`, профиль `a`. Владелец вошёл, создал отдельную комнату `FD-4YDEVR` с 1/2 участниками, дождался «Соединение установлено» и нажал logout при активном WS. Вместо ошибки получено зелёное «Ты вышел из аккаунта», поля очищены. [Перед выходом](screenshots/stage-8-1-fresh-before-logout.png), [исправленный выход](screenshots/stage-8-1-fresh-logout-fixed.png), [финальный выход владельца](screenshots/stage-8-1-owner-final-logout.png).

После повторного входа та же вспомогательная комната восстановилась с 1/2 без join. Она закрыта вне активного раунда: CLOSED, revision 2, новых round/history нет. Последующий logout также штатный; свежий Java-процесс завершился exit 0 после закрытия окна. Основной lifecycle второй раз целиком не заявляется.

```powershell

```

Остаток одной сессии объясняется прерванным первым JVM-сеансом: при перекомпиляции общей `build/classes` с оставленным старым окном возник `NoSuchMethodError`, поэтому его logout не является валидной проверкой новой сборки. Новый login/logout отзывает только свой токен и не отзывает чужую старую сессию по контракту. SQL ради искусственного нуля не менялся; после снятия доказательств весь одноразовый кластер удалён. Чтобы исключить смесь версий классов при следующей разработке, launcher теперь выдаёт каждому запуску отдельную неизменяемую копию application JAR, а не живой `build/classes`. Свежий GUI-повтор использует именно её. Чувствительные пароли, токены и их хеши не публикуются.

## Воспроизведение

Нужны JDK 21, Python 3.9+ и native PostgreSQL 17 binaries. В текущей среде использован Python 3.13 через `py -3`, PostgreSQL находится в `C:\Program Files\PostgreSQL\17\bin`. Runtime-файлы и логи принадлежат `desktop/build/`, не входят в коммит и не являются общими настройками backend. Контроллер не скачивает и не устанавливает PostgreSQL.

Из корня репозитория собрать сервер. Проверять успешный результат каждой команды перед следующей:

```powershell
$env:JAVA_HOME='C:\Users\user\.jdks\corretto-21.0.6'
$env:PATH="$env:JAVA_HOME\bin;$env:PATH"
Push-Location backend
.\mvnw.cmd --batch-mode --no-transfer-progress package '-DskipTests'
Pop-Location
```

Запустить отдельный стенд и оставить процесс работающим. Для нового прогона выбрать новое имя `--run-dir`; существующий каталог контроллер не переиспользует:

```powershell
py -3 .\desktop\scripts\stage8_runtime.py `
    --java-home "$env:JAVA_HOME" `
    --server-port 18091 --db-port 55438 `
    --run-dir desktop/build/stage8-ui-local
```

После `READY` два клиента запускаются в двух отдельных терминалах из корня репозитория:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\desktop\scripts\run-integration-client.ps1 -Profile owner -BaseUrl http://127.0.0.1:18091
```

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\desktop\scripts\run-integration-client.ps1 -Profile partner -BaseUrl http://127.0.0.1:18091
```

Профили используют отдельные `preferences.properties` под `desktop/build/stage8-runtime/`; обычный пользовательский файл настроек не перезаписывается. Gradle подготавливает application JAR и заканчивает работу до запуска клиента, поэтому два окна не конкурируют за долгоживущую задачу `Gradle run`. Каждый запуск получает неизменяемую копию `profile-<profile>/client-<UUID>.jar` и classpath зависимостей, без ссылок на `build/classes` и `build/resources`. Новая компиляция не подменяет классы уже запущенного процесса. Для применения нового кода всё равно нужно закрыть старое окно и запустить новое: это не hot reload.

Пароль и bearer-токен не сохраняются в preferences; оба пользователя регистрируются или входят через UI. Скрипт не включает `--demo`.

Финальный launcher реально проверен с `-Profile a -PrepareOnly`: exit 0, `BUILD SUCCESSFUL` за одну секунду, 5 tasks (1 executed, 4 up-to-date), 67 classpath entries, отдельный application JAR 1 300 989 bytes, прямых ссылок на `build/classes` — 0. `preferences.properties` на этом шаге не создавался. `-PrepareOnly` проверяет подготовку runtime, а не прохождение сценария UI. Дополнительные параметры: `-Width` (840–4096), `-Height` (600–4096); имя `-Profile` содержит 1–32 символа `a-z`, цифры, `_`, `-` и начинается буквой или цифрой. Адрес `-BaseUrl` должен быть HTTP(S) origin без credentials/path/query/fragment. Изменённые launcher переменные окружения восстанавливаются при выходе.

Для штатной остановки сначала закрыть оба окна, затем создать сигнал остановки своего стенда:

```powershell
New-Item -ItemType File -Path .\desktop\build\stage8-ui-local\shutdown
```

Контроллер останавливает только свои Java/PostgreSQL, удаляет созданный им временный кластер и сохраняет логи/SQL. Использовать каталог именно своего запуска; пользовательская БД не затрагивается.
