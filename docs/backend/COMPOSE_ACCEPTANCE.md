# Приёмка двух Compose-окон с Java и сном Windows

**M1–M4 пройдены в настоящем GUI:** два независимых Kotlin/Compose-клиента работали с Java backend и постоянной PostgreSQL; проверены совместная комната, PAUSED/RUNNING после двух сеансов Modern Standby, неизменяемый итог и закрытие комнаты. Это ограниченный ручной прогон, а не завершение всех требований backend-этапа 3.

Дата: **11 октября 2026, Asia/Qyzylorda (UTC+05:00)**. Временные метки ниже приведены в UTC за **10 октября 2026**. Документ подготовлен в `feat/backend-compose-acceptance` от `origin/main` `9287c91` после merge PR #15. При запуске рабочая копия была на `30c8235`, desktop — `8fdb392`; реализация backend между этими документальными checkpoint не менялась.

## Среда и порядок работы

- Два нативных Java-процесса на Windows / Temurin 21.0.12.101, Compose-окна с параметрами 1280×800. Клиент запущен через один предварительный Gradle-экспорт classpath и два прямых `MainKt`, без demo.
- Один Java backend в WSL, `http://127.0.0.1:8090`, PID **71182**; PostgreSQL 17.11 на **5434** с постоянным Compose-volume. Использован существующий `.env`, без disposable/tmpfs-стенда.
- Пользователи `manual_a_1011_01` и `manual_b_1011_01`, комната **FD-U663EE**, FOCUS 25 минут / BREAK 5 минут. Регистрацию и создание/вход выполнил пользователь; наличие обоих участников подтверждено. Дальнейшие действия и наблюдения выполнены в двух настоящих окнах.
- Точные воспроизводимые команды и последовательность — в [MANUAL_ACCEPTANCE.md](MANUAL_ACCEPTANCE.md). Расширенные сценарии — в [INTEGRATION.md](INTEGRATION.md).

Сведения сверены с локальными `session.json` и `observations.jsonl` из `.local/manual-acceptance-20261011/`, снимками и подтверждёнными событиями питания Windows. Время наблюдения таймера и время записи файла снимка различаются; расчёты используют метки наблюдения из сессии.

### Сон и отсчёт

Оба физических перехода подтверждены `Microsoft-Windows-Kernel-Power`: событие **506** входа и **507** выхода из **Modern Standby**. Это интервалы этих событий, а не доказательство классического S3 или остановки монотонных часов.

| Состояние | Вход, UTC | Выход, UTC | Интервал событий |
| --- | --- | --- | ---: |
| PAUSED | `21:15:21.0604296Z` | `21:16:34.5652297Z` | **73.5048001 с** |
| RUNNING | `21:19:36.3419768Z` | `21:21:33.3922865Z` | **117.0503097 с** |

После PAUSED-сна оба остатка остались 24:45. Продолжение запрошено в `21:18:47.297Z`. Для RUNNING записаны следующие независимые пары наблюдений:

| Окно | До второго сна | После второго сна | Календарный интервал между наблюдениями | Уменьшение отсчёта |
| --- | --- | --- | ---: | ---: |
| A | `21:18:52.335Z` — **24:40** | `21:22:19.938Z` — **21:12** | **207.603 с** | **208 с** |
| B | `21:18:59.127Z` — **24:33** | `21:22:26.362Z` — **21:06** | **207.235 с** | **207 с** |

Интервалы между наблюдениями включают время до и после сна; их нельзя выдавать за продолжительность самого сна. Снимки A и B сделаны последовательно, поэтому разные показания на них не означают рассинхронизацию. Во время обоих циклов сохранился Java PID 71182, API без токена отвечал 401, PostgreSQL оставалась healthy. Ручные refresh, relogin или restart не использовались.

## Состояние после прогона

Read-only SQL проверил только собственную комнату **FD-U663EE** и двух её пользователей, без чтения секретных полей и без изменений данных:

- Комната **CLOSED**, revision **16**; 2 участника, **0 active memberships**, ровно 2 раунда и 2 записи истории. Каждый пользователь связан с каждым из двух итогов ровно один раз.
- FOCUS: план **1500 с**, **COMPLETED/MANUAL**, `active_elapsed_ms=271241`. BREAK: план **300 с**, **CANCELLED/ROOM_CLOSED**, `active_elapsed_ms=37026` (**37.026 с**); текущим последним раундом остался BREAK.
- Снимок FOCUS сохраняет исходную незавершённую задачу B. В живой задаче и снимке BREAK — новый текст с «(после фокуса)» и выполненный статус; триггеры неизменяемости истории включены.
- У каждого из этих пользователей одна сессия, **0 неотозванных и 0 действующих сессий** после logout. Эти числа относятся к проверяемым аккаунтам, не ко всей пользовательской БД.

Оба окна оставлены на экране входа. Обычные Java backend и постоянная PostgreSQL **продолжают работать**; остановка или удаление контейнера/volume не выполнялись. `.env`, аккаунты и сохранённая история остаются на месте. Это пользовательская БД, поэтому итог ручного сеанса не описывается как удаление временного стенда.

## Границы доказательства

- При осмотре активировали каждое окно; foreground сам может вызвать восстановление. Этот прогон подтверждает итоговое автоматическое поведение без ручного refresh, но не изолирует heartbeat-only или WS-only путь.
- **Время от пробуждения до готовности не измерено.** Не проверены остановка `nanoTime`, сон непосредственно внутри двухсекундного барьера, все режимы питания и длительный сон.
- LAN, физическое отключение адаптера, живой TTL, просроченный ELAPSED, полная UI-регрессия и Windows-упаковка остаются открытыми. Backend-этап 3 этим отчётом не закрывается.
- Maven `verify`, Gradle test/check и автоматические harness ради GUI/документации не перезапускались. Ранее проверенные **185 + 2 теста и 4 harness** — отдельное доказательство из [WAKE_ACCEPTANCE.md](WAKE_ACCEPTANCE.md), не счётчик тестов этого ручного сеанса.
