# FocusDuo Desktop — план реализации

## Порядок работы

Работа разбита на небольшие этапы. Ориентир каждого этапа — **25–40 минут**, примерно полчаса; это оценка объёма, а не гарантия времени. Загрузка зависимостей, особенности Windows и найденные ошибки могут увеличить срок. Если этап не укладывается в этот ориентир, незавершённая часть фиксируется отдельно, без пропуска проверок и без объявления этапа готовым.

В каждом рабочем заходе выполняется один согласованный этап. В конце записываются результат, выполненные проверки и оставшиеся ограничения. Следующие этапы не выполняются автоматически в том же заходе. По уточнению пользователя от 10 октября проверка Compose-окна и новые скриншоты начиная с этапа 4 отложены до этапа 7; сборка и автоматические тесты выполняются на текущем этапе. Заключительная визуальная регрессия этапа 9 сохраняется.

## Границы и исходные решения

- Основная desktop-ветка прежних этапов: `feat/desktop-mvp`; исправление замечания backend PR #13 вошло в `main` через PR #14. Этап 8.1 подготовлен в `feat/desktop-stage8-1` от `main` `a1e557f`; этап 8.2 — в `feat/desktop-stage8-2` от desktop-коммита `0da9c6c`. Изменения только внутри `desktop/**`; backend и общие файлы репозитория принадлежат другому разработчику. Чужие изменения сохраняются.
- Текущая Windows-упаковка ведётся в `feat/desktop-windows-package` от `main` `467ed63`; приёмка и локальный MSI — в [WINDOWS_PACKAGING.md](WINDOWS_PACKAGING.md). Предыдущий просроченный FOCUS подтверждён на `1a6fa94`; удалённый Tailscale-прогон участников уже зафиксирован отдельно от установленного MSI.
- У desktop собственные Gradle-сборка, wrapper, ресурсы, тесты и документация.
- Стек: Kotlin/JVM, Compose Multiplatform Desktop, Java toolchain 21, Gradle Kotlin DSL, Ktor Client с CIO, kotlinx.serialization, coroutines и StateFlow.
- Окончательный визуальный ориентир — прикреплённый пользователем **светло-зелёный макет с круговым таймером**. Он заменяет прежнее требование тёмного интерфейса и прежний ориентир в `docs/design/`. Локальная копия нового макета: `desktop/docs/design/light-green-reference.png`.
- Контракт API V1 сохраняется. Замена макета меняет визуальное оформление, но не правила авторизации, комнат, таймера и истории.
- Используется стандартная системная рамка окна Windows. Кастомная рамка не входит в первый этап.
- Деморежим запускается только явно: аргументом `--demo` либо кнопкой открытия демо. Он имеет заметную пометку. Ошибка настоящего сервера никогда не переключает приложение на демоданные.
- Базовый адрес настоящего сервера по умолчанию: `http://127.0.0.1:8090`; адрес должен настраиваться.
- Удалённые push, merge и publish выполняются только по отдельному указанию пользователя.

Критерий готовности: проект собирается и запускается; редактирование имени и цели отражается в интерфейсе; деморежим включается явно. Выполненные команды и фактический результат запуска записаны. `FakeRepository`, сеть и поведение таймера на этом этапе не заявляются реализованными.

Результат: wrapper и сборка работают с JDK 21, 5 тестов прошли. ### 6. RealRepository: комнаты, задачи, раунды и WebSocket

**Статус: реализация и автоматические проверки завершены 11 октября 2026; Compose-окно остаётся на этапе 7. Ориентир: 25–40 минут.**

Подключить оставшиеся команды комнаты, целей, задач и раундов, историю и raw JSON WebSocket с bearer в handshake. Все команды отправлять по REST. Применять полные `ROOM_SNAPSHOT`, сравнивать revision внутри одной комнаты. Отображать реальный таймер по серверному снимку и монотонным локальным часам.

Критерий готовности: данные реального режима поступают из репозитория; протокол не расширен самовольно. UI не объявляет завершение по собственному достижению нуля и не изображает online-присутствие партнёра, которого нет в V1.

Добавлены REST-команды создания/входа, цели/задач, настроек, FOCUS/BREAK, pause/resume/finish и закрытия; каждый запрос получает Idempotency-Key, команды существующей комнаты — исходную X-Room-Revision. История и детали читаются с backend. Raw JSON WebSocket использует Authorization в handshake, реальные состояния подключения и актуальный полный snapshot перед разрешением изменений. HTTP и WS применяют общий reducer revision; поздние сообщения прежнего подключения игнорируются. RUNNING отображается по серверному сроку и монотонным локальным часам, PAUSED заморожен, ноль ожидает серверное завершение. Конфликт применяет возвращённый snapshot и показывает ошибку без автоматического повтора. Неоднозначный исход блокирует новые изменения до синхронизации; create/join требует восстановления текущего членства через GET. Добавлены автономные HTTP/WS/TCP и clock/reducer тесты: 143 прошли без ошибок. Отдельная opt-in задача backendRoomSmoke подготовлена; живой backend не был доступен, её запуск и Compose-аудит не объявляются выполненными. Автоматическое reconnect/backoff и сохранение неоднозначного запроса для безопасного повтора остаются этапом 7; пока WS восстанавливается вручную.

### 7. Переподключение, идемпотентность и конфликты

**Статус: завершён 11 октября 2026; автоматические проверки и промежуточный Compose-аудит выполнены. Ориентир: 25–40 минут.**

Реализовать восстановление WS с ограниченными задержками повторов, синхронизацию после восстановления сети и пробуждения ПК, защиту от поздних сообщений старых соединений. До нового полного snapshot запрещать изменяющие действия. Обработать WS `4401`, закрытую комнату, `REVISION_CONFLICT` и неоднозначный исход HTTP-команды.

Этап 6 уже содержит reducer, generation-защиту, первое полное WS-состояние, базовую обработку `4401`/закрытой комнаты и snapshot конфликта. На этапе 7 расширить это до автоматического восстановления, пользовательского разрешения конфликтов и сохранения исходных method/path/body/ключа/revision для повтора; не заменять их новым запросом автоматически.

Критерий готовности: повтор после сетевого сбоя сохраняет исходные запрос, ключ и revision; конфликт предлагает пользователю новое действие, а не бесконечный автоматический повтор. Старые снимки не откатывают UI, ожидаемое закрытие CLOSED-комнаты не запускает бесконечный reconnect.

По просьбе пользователя сюда перенесён промежуточный запуск и аудит реального Compose-окна для экранов и состояний этапов 4–7: вход/регистрация, главная, история и её детали/фильтры, настройки, loading/error, размеры 1280×800 и 1000×700, прокрутка, длинные русские строки и клавиатурный фокус. Сохранить реальные скриншоты и исправить найденные проблемы. Это дополнительная проверка, а не замена заключительной регрессии этапа 9.

Результат этапа: `gradlew.bat check --console=plain` успешен за 12 секунд; 171 тест, 0 failures/errors/skipped. Настоящее Compose-окно проверено в демо и с явным тестовым HTTP/WS-стендом через `RealRepository`: pending/replay без второго изменения, конфликт с сохранением черновика, offline/автоматическое online-восстановление, `4401`, CLOSED после обрыва, история/детали, размеры и системная рамка.
